Part of the in-game test queue. Setup, admin commands and the monster type id table: Session Setup. The stream this sheets entries come from: Crafting — the second loop.

Crafting is the second loop the charter ordered after thumping: turn resources the thumper brings up into an item you equip. It runs NET-18's whole problem in miniature — a crafted item has to arrive in your inventory the same way any created item does, so it cannot start until item delivery is confirmed. The first entry below is that confirmation, and it is the gate for everything after it.

Why this file exists

The stream opened 2026-08-19, the day the vertical slice closed, as a new stream with new goals rather than a ninth milestone on a finished plan. The charter gave the reason: the economy decision is easier to make once resources actually exist in the world, and they do now — thumping is built, verified, and paying out on real ground.

Everything in the stream is a proposal from the charter's survival audit; the user edits it before any of it is scheduled. The audit already settled that crafting is the recoverable case: v1.6 deleted the crafting panel's Lua, but the full Fabrication command set survives in the client binary and AeroMessages, and the engine still exports GetRecipeIds/GetRecipeInfo — Mainframe.lua still calls them. Missing Lua can be authored; a dead engine feed could not. It also settled that a curated subset of the 5,052 resolvable blueprints is a complete answer, and that the server side already has named stubs — RequireResource and RequireResourceFromTarget are stubs, Blueprint_Resources is shipped data that nothing reads — so the work has an address.

The loop cannot open until items can be received. Every crafting entry below ends with an item appearing in your inventory. If PIN's partial InventoryUpdate will not list a created item (the NET-18 defect, still open), a crafted item would arrive the same way any created item does — resolved, listed server-side, never drawn — and no amount of recipe work would show. So the first entry is the client confirmation of the fix that just landed, and nothing past it runs until it passes.

What the fix was. On 2026-08-20 CreateItem was changed to send DynamicFlags = 0x02 — the is_new arrival flag an inventory list reads to draw a new row — instead of IsBound alone, matching the 13 retail ordinary single-item adds exactly and dropping the speculative IsBound. A headless test confirms the created item carries 0x02 and that update is what goes out on the channel; it does not answer the question this sheet asks, whether the client now draws the row. That is a live-client read, and it is the first entry here.

CRAFT-0[x]a created item appears without a resend

Passed in game 2026-08-20, on the second attempt with a different item. createitem 85968 (Heavy Machine Gun) was listed by the client on its own, no dbg_inventory resend. That is NET-18's client confirmation: the 0x02 arrival flag was the fix, and item delivery works. CRAFT1–CRAFT5 are unblocked.

The first attempt failed and the item was at fault, not the server. Three sittings using 20003 (DevTEST Shotgun) showed nothing — and the shotguns were not merely undrawn on arrival, they were absent after a full inventory at login carried eight of them, which no delivery bug can explain. 20003 carries client item flags 0x0800; every item the panel does draw carries 0x4803. Splitting that inventory on the two low bits gives 45 drawn and 17 not, and the 17 are exactly the shotguns, the Battlemedics, the four unnamed items and the three chassis. 35,006 of the game's items are on the wrong side of that line. See DATA-25 — do not test item delivery with 20003.

Blocks CRAFT1–CRAFT5. Run it before any of them.

Read the console output alongside what you see:

CRAFT1[~]A panel reaches fabrication

The client surface. Scoped 2026-08-20 by reading system/gui and the client binary; the entry below is what that found, and it changes the choice this entry was written to make. Steps 1 and 2 ran the same evening and the unknown is settled — see the probe result below.

Repurposing Tinkering is off the table. Its Lua is intact — 2,507 lines across Tinkering.lua and TinkeringView.lua — but it is a different feed entirely: GetTinkerPlansForItem, GetTinkerIngredients, ExecuteTinkeringPlan, and nothing recipe- or fabrication-shaped anywhere in it. It offers a layout to copy and no data path, so it is not the shortcut this entry assumed.

What survives is larger than GetRecipeIds/GetRecipeInfo. Eight recipe functions are still exported by the client binary: those two plus GetRecipe, GetRecipeList, AddRecipeToCart, RemoveRecipeFromCart, CanTrackRecipe and IsTrackingRecipe. A cart means the client still has a notion of queuing a job. Only the first two have a surviving caller — Mainframe.lua, feeding the web panel — so the other six are exports whose behaviour is unknown rather than absent.

There is a dead panel slot to build into. components/MainUI/Panels/FabTest/ is the developers’ own fabrication test screen: the XML shell survives, FabTest.lua is 1,056 bytes of blank lines, and nothing else in the tree references it. Better still, UISets/MainUI.xml names %FF_DOCUMENTS%\Addons as a second component folder, so a panel can be added without touching the Steam install. See Client/Addons.

The server side is defined and empty. Eight fabrication commands (240–247) and eight responses (176–183) have AeroMessages classes and enum entries, and not one has a handler. FabricationFetchAllRecipesResponse is a byte-counted array of recipe ids, which was read at the time as a hard 255-recipe ceiling. It is not one — see the codec note under CRAFT1b. The count byte is a chunk length, not a total.

Settled 2026-08-20: the recipe catalogue is entirely client-side, and the panel leads. FabProbe ran at login against a PIN server that has no fabrication handler of any kind, and the client answered 6,251 recipes anyway. Nothing on commands 240–247 reached the server during the run. A panel can therefore list, describe and cost every recipe in the game before PIN sends a single fabrication message, and CRAFT2 does not have to supply the catalogue.

What the probe found. All eight functions are callable. GetRecipeList() returns 6,251 entries, which is exactly the sum of the per-category calls, so it is the union rather than a separate list:

And the payload behind an id is complete, not a shell. GetRecipeInfo returns 10–12 fields: name, description, inputs, outputs, build_time, max_parallel, required_certs, cert_outputs, research_blueprint_id, head_blueprint_id, resourceTypeId, and stage on refining. Real examples out of the run: 92824 “Slaughter i10”, a Plasma Cannon with 3 inputs and a 19-second build; 75097 “Research Medium Health Packs”, whose output is a certificate rather than an item; 52201 “Pack of Sonic Detonators (10)”, five of which can run at once; 77474 “Raw Resource Refining II”.

One thing worth carrying into CRAFT2 and CRAFT3: recipes carry required_certs, so the cert delivery closed under NET-19 is load-bearing here.

Careful with these 6,251. They are the client’s Lua-facing recipe store, built from dbitems::Blueprints. The client’s fabrication messages do not use it. They resolve against a second, separate store of 285 recipes with a different id space entirely, and 75097 is not in it. CRAFT1b has the detail.

Run first among the real items: it is the only part with a real unknown in it, and the risk should be retired before the server work assumes an answer. Requires CRAFT-0 to have passed — it has.

Pass: a panel lists a recipe, sends a fabrication request, and the request reaches the server. The recipe itself resolving is CRAFT2's job.

That pass condition is unreachable and the entry is superseded. No client-side send exists to reach the server with, so the panel cannot be the thing that opens CRAFT2. CRAFT1b replaces it: prove the client still accepts a server-authored fabrication message. Three further things came out of the same binary read and are worth having on record. The client still prints every fabrication reply to its own console (“Fabrication Recipe List:”, “Recipe Finalized”, “Recipe Aborted”), so a reply is observable with no panel at all. The nineteen unnamed fields of FabricationCommonData1 have names in there — recipe_id, build_points, actions_left, turns_used, quality_points, ingredient_multipliers, started_at, ends_at, upgrade_chance and about twenty more. And there is a client setting called fabrication.enabled whose default and effect are both untested.

Not a finished screen. The charter says the deliverable is a decision with a working spike behind it — a panel that proves the route is open is enough to open CRAFT2.

CRAFT1b[x]The client accepts a server-sent recipe list

Passed in game 2026-08-21, on both signals, three times. Each fabrecipes produced, within the same second, Fabrication Recipe List: and its column header in the client console and FabCart: EVENT ON_FAB_FETCH_RECIPES in Lua. Server 23:58:16 → client elapsed 02:06; 00:00:22 → 04:12; 00:05:10 → 01:00 of the next client session. An unprompted, server-authored fabrication message is accepted, decoded and acted on. That is the premise everything after CRAFT1 rests on, and it is no longer an assumption.

The list arrived empty three times. The header printed with no rows under it, and the Lua event carried a table with one key — event — and no recipes. Two candidates were on the table: PIN’s guess at the wire shape was wrong, or the response is one character’s unlocked set and the client was filtering our ids against certs we do not hold. Settled 2026-08-21, and it was neither.

Settled: PIN was sending ids from the wrong table. Read straight out of FirefallClient.exe and clientdb.sd2, no game session needed.

The response handler (client function 0x8d8bb0) does three things in order. If the list it received is empty it prints -- No Recipes were found. and stops — and that line never appeared, so the ids did arrive and the wire shape is fine. Then, for each id, it looks the id up in a recipe map; an id it cannot find is skipped in silence, printing no row and adding nothing to the Lua event table. And nowhere in it is there a check against certificates. So the unlocked-set theory is out on the code, not on the evidence.

The client keeps two recipe stores with two separate id spaces, and we used the wrong one. Game.GetRecipeInfo and the rest of the Lua functions answer out of a store built from dbitems::Blueprints — 6,251 entries, and where 75097 lives, which is why FabProbe could name it. The fabrication handler resolves against dbfabrication::Recipe: 285 rows, ids 124820–140556. Its 23 four-byte columns are exactly the 92-byte record the disassembled loop walks, with the id at the offset the code reads. None of 75097, 92824, 52201 or 77474 is in it, so all four were dropped. The record was already named in Records/dbfabrication/Recipe.cs; nobody had connected it to this message. Its certificate column is zero on all 285 rows, so there is nothing for a cert filter to filter on even if one existed.

And there is no 255-recipe ceiling. The client’s codec for this array (reader 0xa0a1c0, writer 0xa09910) is chunked: read a byte n, read n ids, and if n was 255, go round again. Any length fits. PIN’s encoder is the Aero definition, which writes exactly one count byte and cannot express the repeat, so one message still tops out at 255 of the 285 rows — a limit on our side now, not the format’s.

Method worth reusing: StaticDB.GetHash(name) in FauFau is the same hash the client uses for its push <imm32>; call table loads, so an unidentified table constant in the binary can be named by hashing candidates until one matches. That is how dbfabrication::Recipe got its name.

CRAFT1 established that the client can never ask for a build, so every fabrication message from here on is one PIN sends unprompted. That is a new thing for this server to do and it has never been tried, so it gets tried on the cheapest message in the set before anything is built on top of it.

fabrecipes sends FabricationFetchAllRecipesResponse — a counted list of recipe ids, nothing else — to your own character. The ids now come from dbfabrication::Recipe: 285 rows, ids 124820–140556. The first three runs sent dbitems::Blueprints ids instead, and that was the whole of what went wrong. The callout below is the working-out.

There are two independent ways to see it land, and either one passes. The client’s own console prints Fabrication Recipe List: followed by a header row and one line per recipe — those strings are still in the binary. And the reply raises ON_FAB_FETCH_RECIPES into Lua, which FabCart binds and logs as FabCart: EVENT fetch_recipes. Nothing shipped binds that event, so if it fires, it fired for us.

The server side is in place: the eight fabrication commands now have handlers rather than falling through to “unrecognized MsgID”, and UpdateShoppingList is decoded and logged instead of warned about.

Pass: Fabrication Recipe List: appears in the client console, or FabCart: EVENT fetch_recipes appears, or both. Either proves the client still accepts a recipe list PIN authored, and CRAFT2 can be built on that. Passed on the envelope 2026-08-21; the rows are step 5 and untested.

No reply in chat at all means the command never reached the server. The first time this was run it was typed as /fabrecipes and the leading slash swallowed it — the server log shows neither the command nor an “Unknown command” line, which is the signature of chat text that never left the client.

Silence is a real result, not a mistake. It would mean the receiving half is gated on something — most likely having asked first, or the fabrication.enabled client setting — and the next move would be to read that setting in game rather than to write more server code.

CRAFT2[ ]Fabrication runs server-side

The server side. Handle the surviving Fabrication command set: resolve a recipe's ingredients against inventory, spend them (RequireResource / RequireResourceFromTarget stop being stubs, Blueprint_Resources gets a reader), and place the output item. Not gated on any decision below — the charter's "none of these block starting" still holds. Can run beside CRAFT1.

Requires CRAFT-0 to have passed — the output item has to be deliverable.

Pass: ingredients are spent and the output item arrives. The RequireResource stubs becoming real and Blueprint_Resources getting a reader are the mechanism; the visible result is the crafted item on screen.

The stubs are the tell. RequireResource and RequireResourceFromTarget currently do nothing — a fabrication that "succeeds" while they are still stubs would place an item for free and hide the bug. Confirm the ingredients actually left the inventory, not just that the item appeared.

CRAFT3[ ]The economy decisions

The decisions, now decidable because resources exist in the world. Three calls: which resource economy (five-stat graded materials, or the level-banded veins the node types are written for); where crafted output lands (1962's item system, or a parallel track free of level-45 balance); how resources are carried in inventory. The user's call; the data supports either economy and imposes neither. Wanted before CRAFT4, not before CRAFT2 — the recipes are priced against whatever CRAFT3 picks.

This is a decision, not a pass/fail entry. The run sheet records the decision and the data behind it; there is no client command that settles it.

Pass: the three decisions are written down with the data behind them. CRAFT4 prices recipes against them.

CRAFT4[ ]A curated recipe set

The first recipes that consume what a thumper brings up and produce something worth equipping, chosen from the 5,052 resolvable blueprints and priced against the economy CRAFT3 picks. The curation approach, not the full set — expanding a working subset is cheap, authoring 5,052 up front is not. Requires CRAFT3 (a price to meet) and CRAFT2 (the recipe to resolve).

Pass: a recipe consumes a real thumper payout, spends its ingredients, and produces an equippable item that arrives on its own.

CRAFT5[ ]The loop closes in game

The exit condition. One sitting: thump a deposit, craft from the payout, equip the result, relog, still have it. This is the whole stream end to end — resource gathering (already built and verified), fabrication, equip, and persistence — and it cannot pass until every entry before it has. Requires CRAFT0 (delivery), CRAFT2 (fabrication), CRAFT4 (a recipe that consumes a thumper payout), and Persistence (the item survives a relog).

Pass: the item you crafted from a thumper payout is equipped and still there after a relog. The loop is closed.
