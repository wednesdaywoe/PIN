Tests commits d4aba6b (cooldowns) and 0083602/b76744e (target commands), merged into arclight as 6131602. Until then the server sent every ability a fixed 300 ms global cooldown and never checked one. Now CooldownSet keeps the client's three kinds — per ability, per category, and global — and the activation reply carries the real ones.

Every entry uses Charge, ability 35366, on the Dreadnaught, in ability slot 0 (default button 1). Its chain (SDBQuery ability 35366) is:

  • TimeCooldown checks the local, global and category 67 cooldowns, and fails the use if any is running.
  • LoadRegisterFromItemStat reads stat 1051, "Charge Recharge", off the loadout.
  • InstantActivation inflicts a 300 ms global cooldown and a category 67 cooldown of 1000 ms × Charge Recharge — ×0.9 more with item 85809 equipped.

The Charge Recharge value depends on the whole loadout, so the expected length is read off the log rather than written here. Three log lines were added for this page:

  • Ability 35366 inflicts cooldowns: global 300 ms, local 0 ms, category 67 <N> ms — what the server applied.
  • Ability 35366 refused: <which> cooldown has <N> ms left — a use the server turned down.
  • Ability 35366 failed its chain, so no AbilityActivated was sent — a key press the server rejected.

Before starting, confirm the running server has them (it should print a number above 0):

python3 -c "print(open('/home/jiiwii/Games/PIN/GameServer/GameServer.dll','rb').read().count('inflicts cooldowns'.encode('utf-16-le')))"
COOLDOWN-1[x]The cooldown on screen is the length the server applied

The main check. The client draws the cooldown from the reply the server sends, so a wrong number shows up as a timer that's too short, too long, or missing.

grep -aE "35366 (inflicts|refused|failed)|ActivateAbility 35366" ~/Games/PIN/logs/GameServer.log | tail -10
  • Pass: one inflicts cooldowns line with a category 67 value above 0, one ActivateAbility 35366 at line, and the on-screen sweep within about half a second of the category value.
  • Fail, no sweep at all: the client got no cooldown. If the log shows failed its chain, the chain stopped before InstantActivation; record the line.
  • Fail, category 67 reads 0 ms: Charge Recharge read as 0. Run grep -a "LoadRegisterFromItemStat" ~/Games/PIN/logs/GameServer.log | tail -3 and record it.
  • Fail, the sweep is a different length from the log: record both numbers.

Passed 2026-10-02. Every press logged global 300 ms, local 0 ms, category 67 13500 ms — Charge Recharge read as 13.5 on this loadout — and the sweep on screen matched.

COOLDOWN-2[x]The server refuses a use while the cooldown runs

The client checks cooldowns itself and won't send a press while the icon is sweeping, so a key press can't test the server's check. The admin ability command runs the chain on the server directly, which can.

grep -aE "35366 (inflicts|refused)" ~/Games/PIN/logs/GameServer.log | tail -4
  • Pass: an inflicts cooldowns line, then refused: category 67 cooldown has <N> ms left with N positive and below the category length. Only the first use charges.
  • Fail: two inflicts lines and no refused — the second command came after the cooldown ended, or the check isn't running. Repeat with the second command typed faster; if it still passes through, record both lines.

Also note whether the icon sweeps after step 2. The admin path sends a cooldown update but no activation reply, so a missing sweep here is worth recording but is not a failure.

Passed 2026-10-02. ability 35366 at 20:31:13 inflicted the cooldown; the second at 20:31:16 logged refused: category 67 cooldown has 10117 ms left.

COOLDOWN-3[x]Charge works again once the cooldown ends

Guards against a cooldown that never clears, from a timestamp compared the wrong way. The gaps straddle 65 seconds because a 16-bit clock wraps there.

grep -aE "35366 (inflicts|refused|failed)" ~/Games/PIN/logs/GameServer.log | tail -6

Pass: Charge fires all three times, three new inflicts lines, no refused or failed lines from these presses.

Passed 2026-10-02. Eight presses between 20:29:52 and 20:34:17, at gaps from 14 s to 94 s, each logged a fresh inflicts line and none was refused or failed.

COOLDOWN-4[x]Charge still finds its targets after the target-command rewrite

The same merge rewrote how abilities pick and filter targets. A smoke check, not a full sweep: Charge's opening effect lands on yourself, and its impact on what it hits.

grep -aE "Id 15252|Id 15216|Pushing new target" ~/Games/PIN/logs/GameServer.log | tail -12
  • Pass: effect 15252 (windup) is applied to you, then effect 15216 (impact) is applied to you and its chain logs Pushing new target with the Fiend's entity id.
  • Fail, 15252 missing: TargetSelf broke. Fail, 15216 lands on you instead of the Fiend, or on nothing: the impact's target list broke. Record the lines either way.

Charge's impact was never confirmed on a monster before this merge, so a miss here may be old. If it fails, rerun on git checkout 4c3f3be before blaming the rewrite.

Passed 2026-10-02, with the expected lines corrected. 15252 landed on the player at 20:34:17. 15216 lands on the player too, not the Fiend; its chain then logged Pushing new target: CharacterEntity (2305613035190081536), the Fiend, at 20:34:18. That is the impact finding its target.
